# Clean Architecture Overview & Assessment Checklist

## Core Philosophy & The Dependency Rule
* **The Dependency Rule:** Source code dependencies must only point inward toward higher-level policies. Nothing in an inner circle can know anything at all about something in an outer circle (such as classes, functions, variables, or database formats).
* **Framework Independence:** The architecture does not depend on the existence of a library of feature-laden software. Frameworks are treated as tools to be used rather than forcing your system into their constraints.
* **Testability:** Business rules can be tested without the UI, database, web server, or any other external element.
* **UI & Database Independence:** The user interface and database can be swapped out (e.g., moving from a web UI to a console, or from SQL to a NoSQL document store) without changing the core business rules.
* **Independent of External Agencies:** Business rules simply do not know anything at all about the outside world or third-party integrations.

## The Concentric Layers (Inner to Outer)
* **Entities (Enterprise Business Rules):** Encapsulate enterprise-wide critical business rules and data structures. They are the least likely to change when something external changes.
* **Use Cases / Interactors (Application Business Rules):** Contain application-specific business rules and orchestrate the flow of data to and from the Entities to achieve a specific user goal.
* **Interface Adapters:** Convert data from the format most convenient for the Use Cases and Entities into the format most convenient for external agencies (such as Controllers, Presenters, Gateways, and Repository implementations).
* **Frameworks & Drivers:** The outermost layer composed of frameworks and tools such as the database, web framework, UI, and external devices. Very little code is written here other than glue code to communicate with the inner layer.

## Key Architectural Mechanisms
* **Dependency Inversion Principle (DIP):** When control flows outward (e.g., a Use Case needs to call a database), the Use Case defines an interface in the inner layer, and the outer layer implements it to keep source code dependencies pointing inward.
* **Boundary Crossing & DTOs:** Data crossing layer boundaries should take the form of simple, isolated data structures (Data Transfer Objects). Never pass database rows or framework-specific models directly into inner layers.
* **Humble Object Pattern:** Keep components that are hard to test (like UI views or database drivers) as thin and logic-free as possible, moving all testable behavior into inner classes.
* **Screaming Architecture:** The top-level folder structure and module names should clearly communicate what the system *does* (e.g., `Billing`, `Inventory`, `Shipping`) rather than what framework it uses (e.g., `Controllers`, `Models`, `Views`).
