# Entity-Driven Architecture Overview & Assessment Checklist

## Core Philosophy & Data-Centric Design
* **Database-First Modeling:** System design starts with the relational database schema (tables, columns, foreign keys), and application code is structured to mirror those tables directly.
* **Shared Canonical Data Model:** A single set of entity classes (often generated or mapped directly via an ORM like Entity Framework, Hibernate, or Prisma) is shared across the database, business logic, and API layers.
* **CRUD-Centric Operations:** System capabilities are modeled around standard Create, Read, Update, and Delete actions on individual records rather than explicit business tasks or domain behaviors.
* **Centralized Relational Integrity:** Data consistency, relationships, and constraints rely heavily on database features (foreign keys, unique constraints, triggers, and transactions) rather than domain encapsulation.

## Typical Layered Structure
* **Presentation / API Layer:** Exposes REST or GraphQL endpoints mapped directly to underlying database resources (e.g., `GET /users`, `PUT /orders/{id}`).
* **Service / Business Logic Layer:** Contains procedural scripts or "Manager" classes that fetch entities, modify their properties, and save them back to the database.
* **Data Access Layer (DAL):** Uses an ORM or generic repositories (`IRepository<T>`) to perform standard database queries and persistence for every table.
* **Database Layer:** Acts as the single source of truth for the entire application, often shared across multiple modules or services.

## Characteristics & Behavioral Patterns
* **Anemic Domain Models:** Entities act primarily as passive data containers (getters and setters) with little to no encapsulated business behavior or invariant protection.
* **Generic Repositories:** Data access relies on reusable CRUD abstractions per entity table rather than Aggregate-scoped persistence boundaries.
* **Bi-Directional Navigation:** Entities frequently hold direct object references to related entities across the entire schema, allowing developers to traverse large object graphs easily (which can also lead to lazy-loading traps).
* **Tight Schema Coupling:** Changes to database columns or table relationships often ripple upward, requiring updates across services, DTOs, and API contracts.

## Assessment & Trade-Off Checks
* **Best Fit (Simple & Data-Heavy Apps):** Ideal for straightforward CRUD applications, internal admin portals, reporting tools, and MVPs where speed of delivery matters more than complex domain modeling.
* **Complexity Ceiling:** Watch for signs that the system has outgrown Entity-Driven Architecture—such as bloated service classes ("God Services"), scattered validation rules, and fragile side effects when updating shared tables.
* **N+1 Query & Over-Fetching Risks:** Check whether exposing ORM entities or relying on lazy loading causes unintended database queries or accidental exposure of sensitive fields over the API.
